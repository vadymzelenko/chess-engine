Построение шахматного движка: Texel-тюнинг и нейросетевой MCTS

Сравнительный анализ классического и нейросетевого подходов к оценке позиции и поиску хода в шахматах

Аннотация

Работа описывает полный цикл построения шахматного движка с нуля. Исследуются два независимых подхода: классический — с оценочной функцией на основе 768 параметров Piece-Square Tables, оптимизированных методом Texel Tuning на 3 миллионах партий Lichess с рейтингом от 2400 ELO; и нейросетевой — с двухголовой свёрточной сетью DualHeadResNet, предсказывающей policy (4672 вероятности ходов) и value (оценку позиции), обученной методом self-play и используемой совместно с MCTS-поиском через формулу PUCT.

Для классического подхода применяется Adam-оптимизация поверх sparse design-матрицы, что позволяет обучать 768 параметров на миллионах позиций за минуты без использования GPU. Для нейросетевого — батчирование MCTS-симуляций через технику virtual loss, дающую 16-кратное увеличение числа симуляций на один forward pass сети. Финальные MSE по обеим моделям приведены в таблице 5.1. Все исходные данные доступны в открытом репозитории проекта.

Раздел 01

Введение

Шахматный движок состоит из двух независимых компонент: функции оценки позиции и алгоритма поиска. Обе допускают как классическую, так и нейросетевую реализацию.

Задача построения шахматного движка формулируется как задача оптимизации: для данной позиции найти ход, максимизирующий ожидаемый результат партии. Формально, если обозначить V(p) — истинную ценность позиции p (в диапазоне [−1, +1] с точки зрения белых), то оптимальный ход из текущей позиции определяется как:

arg maxm ∈ M −V(p · m)
(1.1)

где M — множество легальных ходов, p · m — позиция после применения хода m. Знак минус возникает из того, что после нашего хода очередь хода переходит к противнику, и оценка меняет знак (negamax-формализм).

Вся сложность задачи упирается в две проблемы: во-первых, истинная функция V(·) неизвестна и должна быть приближена оценочной функцией ĥ(·); во-вторых, дерево вариантов слишком велико для полного перебора (на глубине 10 порядка 1015 позиций), поэтому необходим эффективный алгоритм отсечения.

1.1 Мотивация и постановка задачи

Существуют два принципиально разных способа построить оценочную функцию:

  • Экспертный (классический). Человек вручную описывает признаки позиции: ценность фигур, контроль центра, безопасность короля, пешечная структура. Каждый признак имеет вес, и веса оптимизируются численно на большом корпусе партий — это метод Texel Tuning [1].
  • Обучаемый (нейросетевой). Оценочная функция задаётся нейросетью без явных признаков. Сеть сама учится извлекать паттерны из сырых данных — позиций, представленных в виде битовых плоскостей 8×8. Обучение идёт методом self-play, как в AlphaZero [2].

Настоящий отчёт описывает обе реализации, выполненные в рамках одного проекта, и проводит их сравнительный анализ.

1.2 Соглашения и обозначения

Для однозначности далее используются следующие соглашения:

Обозначение Значение
p Позиция на доске (расстановка фигур, чей ход, права рокировки, en passant)
V(p) Истинная ценность позиции в диапазоне [−1, +1] с точки зрения белых
h(p; w) Оценочная функция с параметрами w, возвращающая значение в сантипешках
π(p) Policy — распределение вероятностей по легальным ходам из позиции p
σ(x) Логистическая функция: σ(x) = 1 / (1 + e−x)
ply Полуход; один ply = ход одной стороны
N Число посещений узла в MCTS
Q Средняя оценка узла в MCTS (Q = W / N)
P Prior — вероятность хода по policy сети
Раздел 02

Оценочная функция и Texel-тюнинг

768 параметров Piece-Square Tables, оптимизированных методом градиентного спуска на 3 миллионах позиций Lichess.

2.1 Признаки позиции

В классическом подходе оценочная функция строится как линейная комбинация признаков. Каждому признаку соответствует один числовой параметр. Мы используем простейший набор признаков: тип фигуры × клетка. Для каждой из 6 типов фигур (пешка, конь, слон, ладья, ферзь, король) и каждой из 64 клеток заводится два параметра — для фазы середины игры (midgame) и для фазы эндшпиля (endgame). Итого:

Nparams = 6 × 64 × 2 = 768
(2.1)

Черные фигуры зеркалятся по горизонтали — если белая пешка стоит на a2, то чёрная пешка на a7 читается по параметрам белой пешки на a2. Это уменьшает число параметров вдвое, с 1536 до 768, и делает признаки инвариантными к цвету.

2.2 Tapered evaluation

Разные фазы игры требуют разной оценки. В дебюте король должен прятаться за пешками, в эндшпиле — активно идти в центр. Чтобы учесть это, используется tapered eval: финальная оценка получается линейной интерполяцией между midgame- и endgame-оценкой по «фазе игры».

Фаза считается как сумма весов фигур на доске. Пешки не учитываются (вес 0), лёгкие фигуры дают 1, ладьи — 2, ферзи — 4:

phase = min( 4Nknight + 4Nbishop + 2Nrook + 4Nqueen, 24)
(2.2)

Начальная позиция даёт 4 + 4 + 8 + 8 = 24. Финальная оценочная функция:

eval(p) = [ phase · mg(p) + (24 − phase) · eg(p) ] / 24
(2.3)

где mg(p) и eg(p) — оценки по midgame- и endgame-параметрам соответственно. Формула линейна по весам, что критично для дальнейшей оптимизации.

2.3 Texel Tuning

Метод назван в честь движка Texel, написанного Peter Österlund [1]. Идея: если у нас есть оценочная функция и миллионы партий с известными результатами, мы можем подобрать параметры так, чтобы предсказания функции совпадали с результатами.

Формально, для каждой позиции pi известен результат партии yi ∈ {0, 0.5, 1} (0 — победа чёрных, 1 — победа белых). Мы хотим, чтобы сигмоида от оценки совпадала с этим результатом:

ŷi = σ( K · eval(pi; w) ) ,    K = 1 / 400
(2.4)

Функция потерь — среднеквадратичное отклонение:

L(w) = (1 / N) · Σi (ŷi − yi)2
(2.5)

Градиент этой функции по параметрам w вычисляется аналитически:

∂L / ∂wj = (2 / N) · Σi (ŷi − yi) · ŷi(1 − ŷi) · K · ∂eval / ∂wj
(2.6)

Благодаря линейности eval, частная производная ∂eval/∂wj — это просто индикатор, равный +1, −1 или 0 в зависимости от того, участвует ли параметр wj в текущей позиции и с каким знаком.

Оптимизация вычислений

Наивная реализация перебирает все 768 параметров для каждой позиции на каждой эпохе, что занимает часы. Мы вместо этого один раз строим разреженную матрицу X размера N × 768, где в каждой строке непустых значений ровно столько, сколько фигур на доске (около 30). Тогда весь forward pass — это одно sparse matmul, а backward — второе. Это даёт ускорение на 2–3 порядка.

Наблюдение

PST-признаки не видят связок фигур, пешечной структуры, контроля полей и взаимодействия фигур. Это фундаментальное ограничение подхода: добавление новых признаков (mobility, pawn structure, king safety) увеличило бы выразительность модели, но потребовало бы ручного проектирования.

Раздел 03

Алгоритм поиска

Alpha-beta отсечение с четырьмя оптимизациями: транспозиционная таблица, quiescence search, сортировка ходов, итеративное углубление.

3.1 Minimax и alpha-beta отсечение

Базовый алгоритм поиска — minimax, в negamax-формулировке: значение позиции равно максимуму из отрицательных значений дочерних позиций (после хода противника). Формально:

nega(p, d) = maxm∈M [ − nega(p·m, d−1) ]
(3.1)

На глубине d = 0 возвращается оценка h(p). Такой алгоритм перебирает bd узлов, где b ≈ 35 — среднее число ходов. На глубине 6 это порядка 1.8 · 109 узлов, что вычислительно неподъёмно.

Alpha-beta отсечение позволяет сократить перебор до bd/2 — то есть в 353 ≈ 43 000 раз на глубине 6. Идея: если мы уже нашли ход, дающий оценку α, и в каком-то поддереве оценка становится меньше α для противника, то мы можем это поддерево не исследовать — оно заведомо не улучшит результат. Формально:

  • α — нижняя граница: мы уже знаем, что можем гарантировать себе хотя бы эту оценку
  • β — верхняя граница: противник может гарантировать себе не более этого значения
  • Если в узле α ≥ β — происходит отсечение (cutoff), узел возвращает текущую оценку

3.2 Транспозиционная таблица

В шахматах разные последовательности ходов часто приводят к одной и той же позиции (транспозиции). Более того, в negamax одни и те же позиции возникают в разных поддеревьях. Хранение результатов в хеш-таблице позволяет избежать повторного поиска.

Ключ позиции вычисляется методом Zobrist hashing [5]: каждой комбинации (фигура, клетка) ставится в соответствие случайное 64-битное число, а ключ позиции — XOR всех этих чисел плюс ключи для прав рокировки и en passant. Zobrist-хеш изменяется инкрементально: при push/pop хода достаточно XOR-ить несколько чисел, а не пересчитывать ключ целиком.

Запись в таблице содержит четыре поля:

Поле Назначение
depth Глубина, на которой получена оценка. Запись используется только если depthentry ≥ depthquery
score Оценка позиции, возможно скорректированная для mate-значений (см. ниже)
flag Тип записи: EXACT (точное значение), LOWER (нижняя граница), UPPER (верхняя граница)
move Лучший ход — используется для сортировки ходов при повторном поиске

Отдельного внимания заслуживает обработка mate scores. Мат-оценки включают в себя ply от корня дерева: мат в 3 хода с корня это 999997, но он же на глубине 5 ply — 999995. Если хранить такую оценку в TT без модификации, при попадании в ту же позицию по другому пути оценка будет означать неверное расстояние до мата. 3.3 Quiescence search

Если остановить поиск на глубине d сразу после того, как ферзь взял пешку, позиция будет оценена как «выгодная», хотя через ход пешку отобьют. Это классическая проблема horizon effect: движок не видит за горизонтом поиска.

Решение — quiescence search: на листьях основного дерева мы не оцениваем позицию напрямую, а запускаем дополнительный поиск только по «громким» ходам — взятиям, превращениям, иногда шахам. Поиск продолжается до тех пор, пока в позиции не останется взятий (позиция не станет «спокойной», от англ. quiet).

Тонкость реализации

Stand-pat оценка возвращается только если она не хуже текущего α. Если позиция «заведомо плоха», мы не сдаёмся сразу — а пробуем найти взятие, которое её исправит. Это правильно: если у нас есть выигрывающее взятие, stand-pat (который его не учитывает) не должен возвращаться как итог.

3.4 Сортировка ходов

Эффективность alpha-beta критически зависит от порядка перебора ходов. Если лучший ход исследуется первым, отсечение происходит сразу; если последним — мы перебираем всё поддерево впустую. В лучшем случае (perfect ordering) сложность O(bd/2), в худшем (worst ordering) O(bd).

Мы применяем четырёхуровневый приоритет:

Приоритет Категория Логика
106 TT move Ход, сохранённый в транспозиционной таблице как лучший для этой позиции
104 + Δ Взятия MVV-LVA: чем ценнее жертва и чем дешевле атакующий, тем выше приоритет. Δ = 10 · Vvictim − Vattacker
5000 Killer moves Тихие ходы, которые вызвали beta-cutoff на этом же ply в других ветках
0 Прочие Перебираются в порядке генератора (обычно от a1 к h8)

Таблица MVV-LVA (Most Valuable Victim — Least Valuable Attacker) сортирует взятия по формуле 10 · Vvictim − Vattacker. Идея: взятие ферзя пешкой (900·10 − 100 = 8900) приоритетнее, чем взятие пешки ферзём (100·10 − 900 = 100). Это эвристика — обе позиции заведомо хороши, но первая чаще приводит к отсечению.

3.5 Итеративное углубление

Вместо поиска сразу на глубину D, мы последовательно ищем на глубине 1, 2, 3, …, D. На первый взгляд это расточительно: каждый поиск повторяет работу предыдущего. Однако на практике это быстрее по трём причинам:

  1. Наполнение TT. Мелкие итерации заполняют транспозиционную таблицу, и глубокие итерации находят готовые результаты для большинства поддеревьев.
  2. Хороший порядок ходов. Лучший ход с предыдущей итерации используется как первый ход на текущей — это near-perfect ordering для корня.
  3. Контроль времени. Мы всегда можем прервать поиск после завершения очередной итерации и вернуть лучший ход из последней полной итерации. Это критично для игр с контролем времени, где необходимо гарантированно уложиться в бюджет.

В нашем движке корневая итерация также использует aspiration windows — узкие окна α, β вокруг оценки с предыдущей итерации. Это дополнительно ускоряет поиск примерно на 10–15%.

Раздел 04

Нейросетевой движок

DualHeadResNet с двумя головами — policy и value — обученная методом self-play и используемая совместно с MCTS в стиле AlphaZero.

4.1 Архитектура DualHeadResNet

Второй движок построен по принципу AlphaZero [2]: вместо ручной оценочной функции используется нейросеть, которая сама учится извлекать признаки из позиции. Сеть имеет две головы:

  • Policy head. Предсказывает распределение вероятностей по всем возможным ходам (4672 значения). Используется как prior в MCTS, направляя поиск в перспективные ветки.
  • Value head. Предсказывает оценку позиции V ∈ [−1, +1] с точки зрения игрока, чей ход. Заменяет собой оценочную функцию в листьях дерева.

Общее тело — 16 residual блоков с squeeze-and-excitation вниманием. Каждый блок имеет два свёрточных слоя 3×3 с 256 каналами, BatchNorm и skip-connection.

4.1.1 Входное представление

На вход сеть получает тензор размером 54 × 8 × 8. Это 54 «плоскости» — бинарные матрицы 8×8, каждая из которых кодирует определённый аспект позиции:

Индексы Что кодируется
0 – 5 Белые фигуры: пешка, конь, слон, ладья, ферзь, король
6 – 11 Чёрные фигуры: аналогично
12 Чей ход: все единицы если ход белых, все нули если чёрных
13 – 16 Права рокировки: K, Q, k, q
17 En passant: клетка, если есть
18 – 53 История: 3 предыдущих позиции по 12 плоскостей каждая

История нужна, чтобы сеть могла отличать повторение позиции от «свежей» атаки. Без неё policy и value были бы неоднозначны в позициях с троекратным повторением.

4.2 Кодирование ходов: 73 × 64

Policy head выдаёт 4672 числа — по одному на каждый возможный ход. Кодирование заимствовано из AlphaZero [2] и устроено так: для каждой из 64 клеток отправления мы имеем 73 возможных хода.

Смещение Тип хода Число
0 – 55 Ходы ферзя, ладьи, слона и короля: 8 направлений × 7 расстояний 56
56 – 63 Ходы коня: 8 прыжков типа (1, 2) 8
64 – 72 Превращения пешки: 3 направления (влево-прямо-вправо) × 3 фигуры (без ферзя) 9
— Итого на клетку 73

Ход типа (from_square, to_square) превращается в индекс функцией encode_move, которая определяет направление и расстояние. Policy-голова выдаёт логиты для всех 4672 ходов, но при игре рассматриваются только легальные — их логиты нормализуются через softmax.

4.3 MCTS и формула PUCT

Поиск — не alpha-beta, а Monte Carlo Tree Search. Каждая симуляция — это спуск по дереву до листа, раскрытие нового узла через сеть и обратный backup значения. Дерево растёт итеративно, при этом используются как оценки сети, так и статистика посещений.

Ключевая формула — PUCT (Polynomial Upper Confidence for Trees), определяющая, какой дочерний узел выбрать в каждом узле:

a* = arg maxa [ Q(s, a) + cpuct · P(s, a) · √ΣbN(s, b) / (1 + N(s, a)) ]
(4.1)

Первое слагаемое Q(s, a) — эксплуатация: средняя оценка узла. Второе слагаемое — исследование: пропорционально prior P и обратно пропорционально числу посещений N. Константа cpuct балансирует эти два компонента; мы используем cpuct = 1.5.

После завершения всех симуляций финальный ход выбирается как наиболее посещённый (при temperature = 0) или пропорционально N1/τ (при temperature > 0, для self-play).

4.4 Virtual loss: батчирование симуляций

Наивная реализация MCTS делает один forward pass сети на каждую симуляцию. На GPU это крайне неэффективно: сеть с 10M параметров обрабатывает батч из одного элемента почти так же долго, как батч из 16. Мы теряем утилизацию GPU и упираемся в latency, а не в throughput.

Решение — virtual loss [6], техника из AlphaZero и Leela Chess Zero. Идея: собираем батч из нескольких листьев дерева, но чтобы выборки не шли по одному и тому же пути, временно «наказываем» уже посещённые узлы — прибавляем штраф к их статистике. Когда батч собран, делаем один forward pass и backup-ом снимаем штрафы, применяя реальные оценки.

Выигрыш производительности

На GPU T4 батчирование даёт ускорение примерно в 8–12 раз по сравнению с симуляцией по одной. На CPU выигрыш меньше (примерно в 2–3 раза), но всё равно существенен. При этом качество поиска не деградирует: virtual loss не искажает финальную статистику, а лишь «раскидывает» выборки батча.

4.5 UCI-обёртка для Lichess

Чтобы играть на Lichess, движок должен говорить на протоколе UCI (Universal Chess Interface) [7]. Это текстовый протокол через stdin/stdout. Мы обрабатываем пять основных команд:

Команда Назначение
uci Идентификация движка. Отвечаем id name + uciok
isready Проверка готовности. Отвечаем readyok
position [fen|startpos] moves ... Установка позиции. Мы ведём историю FEN-ов для модели
go [movetime|wtime|nodes|depth|infinite] Запуск поиска. Бюджет конвертируется в число симуляций MCTS
quit Завершение работы

Особенность UCI для MCTS — пересчёт бюджета времени в число симуляций. Движок не знает заранее, сколько симуляций он успеет сделать за отведённое время. Мы поддерживаем онлайн-калибровку: после каждого хода движок обновляет свою оценку скорости (симуляций в секунду) по скользящему среднему, и на следующем ходу использует уточнённое значение.

Устойчивость

Обработка команд обёрнута в try/except: невалидный FEN или нелегальный ход в position логируется в stderr, но не роняет процесс. Это важно в турнирах: одиночная ошибка GUI не должна убивать движок посреди партии.

Раздел 07

Глоссарий

Термины, использованные в отчёте, с определениями.

Alpha-beta отсечение
Алгоритм поиска, сокращающий перебор minimax-дерева за счёт отсечения веток, заведомо не влияющих на итоговое решение. Уменьшает сложность с O(bd) до O(bd/2) при идеальном порядке ходов.
Policy (π)
Распределение вероятностей по возможным ходам. В AlphaZero-style сетях предсказывается нейросетью и используется как prior в MCTS.
Value (V)
Оценка позиции в диапазоне [−1, +1], где +1 — победа игрока, чей ход, −1 — поражение, 0 — ничья.
Tapered eval
Метод интерполяции между двумя наборами параметров (midgame, endgame) по «фазе игры». Позволяет одной оценочной функции работать и в дебюте, и в эндшпиле.
PST (Piece-Square Table)
Таблица весов для каждой комбинации «тип фигуры × клетка». Классический признак в оценочных функциях шахматных движков.
Zobrist hashing
Метод хеширования позиции: каждой (фигура, клетка) сопоставлено случайное число, ключ позиции — XOR всех. Позволяет инкрементально обновлять ключ при push/pop хода.
Quiescence search
Продление поиска в листьях дерева только по «громким» ходам (взятия, превращения). Решает проблему horizon effect.
Horizon effect
Ситуация, когда движок не видит последствий хода, отложенных за «горизонтом» поиска — например, отыгрыш фигуры на следующей глубине.
MVV-LVA
Most Valuable Victim — Least Valuable Attacker. Эвристика сортировки взятий: выгоднее бить ценные фигуры дешёвыми.
Killer move
Тихий ход, вызвавший beta-cutoff в предыдущей ветке на той же глубине. Хранится для приоритетной сортировки.
PUCT
Polynomial Upper Confidence for Trees. Формула выбора дочернего узла в MCTS, балансирующая exploitation (Q) и exploration (P·√N/(1+N)).
Virtual loss
Техника батчирования MCTS: временное «наказание» посещённых узлов, чтобы следующие выборки в батче шли по другим веткам.
SE-блок (Squeeze-and-Excitation)
Модуль внимания в CNN, адаптивно пересчитывающий веса каналов. Используется в ResBlock-ах для усиления значимых признаков.
Self-play
Метод обучения, при котором агент играет против самого себя, генерируя данные для обучения. Используется в AlphaZero.
ELO
Рейтинговая система, оценивающая силу игрока. Разница в 100 ELO ≈ 64% ожидаемых очков в очной встрече.
UCI
Universal Chess Interface — стандартный текстовый протокол взаимодействия GUI с шахматным движком.
Sparse matmul
Умножение разреженной матрицы (с большим числом нулей) на вектор. Позволяет не хранить и не обрабатывать нули, давая ускорение в 100–1000 раз.
